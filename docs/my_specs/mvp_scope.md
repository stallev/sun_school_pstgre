# MVP и post-MVP — распределение функций

**Версия:** 1.1 · октябрь 2026
**Связанные документы:** `sunday_school_data_analytics_spec.md` (v3.2, далее — «спецификация»), `achievements_spec.md`, `DESIGN_SYSTEM.md`, прототип `sunday_school_prototype.html`.
**Статус:** решения владельца от 10 октября 2026 — семьи, роль родителя, голосовая проверка стихов с помощью AI, **достижения и штрафы** переносятся в post-MVP; схема базы данных создаётся сразу целиком, включая post-MVP.

---

## 1. Цель MVP

**MVP заменяет действующее приложение для учителей и администратора.** Критерий готовности: реальная группа ведётся в новой системе — уроки, проверка ДЗ, кирпичики, аналитика, — а старое приложение переведено в режим только для чтения.

Чего MVP не делает: не открывает приложение родителям, не проверяет стихи голосом, не выдаёт достижения и штрафы — ни автоматически, ни вручную. Всё это — post-MVP, по волнам (раздел 3).

Почему так. Родители и голос — это новые сценарии, их ценность ещё не проверена; учителям же нужно работающее приложение уже сейчас. Каждая неделя без MVP — неделя жизни на старой системе (Amplify / DynamoDB), которую вы уже решили заменить.

## 3. Post-MVP: три волны

Порядок — по зависимостям и риску, а не по важности. Каждая волна начинается, когда предыдущая работает у реальных пользователей.

### Волна 1 — достижения и штрафы (решение владельца: post-MVP)

| Что | Документ |
|---|---|
| Каталог достижений и штрафов | `achievements_spec.md`, разделы 2, 6 |
| Автоматический пересчёт по событию «проверка завершена» с доказательствами | ДС-3, ДС-6, ДС-11, ДС-12 |
| Ручная выдача с уроками-доказательствами, отзыв | ДС-5, ДС-7, ДС-13 |
| Режим «Достижения и штрафы» группы | ДС-14 |
| Штрафы: выдача, снятие | ШТ-1…ШТ-10 |
| Бонус и штрафы в «набрано» кирпичиков | БП-11, ДС-10 |
| Перенесённые из старого приложения выдачи становятся видны | Раздел 13 |

**Почему первой.** Нужна только учителю и админу; данные уже есть (проверки ДЗ из MVP); не требует семей. Основной риск — алгоритм пересчёта — закрывается тестами чистой функции (`achievements_spec.md`, 7.3).

### Волна 2 — семьи и родители

| Что | Спецификация |
|---|---|
| Семьи: страница семьи, взрослые и дети, правила СМ-1…СМ-10 | 2.3, 3.9 |
| Роль parent при одобрении заявки: связать со взрослым семьи, добавить в семью ребёнка, создать семью | 2.4 |
| Электронное согласие на данные ребёнка; отзыв = запрос на удаление | СО-1, СО-2, СО-6 |
| Экраны родителя: успехи ребёнка, динамика, кирпичики, календарь, «Данные и согласия», «Моя семья» | 9.2, БП-9 |
| Запрос на удаление данных ребёнка самим родителем | УД-1 |
| Контакты семьи у учителя | СМ-8 |
| Еженедельный дайджест родителю (достижения, штрафы, сданное позже) | ДС-8, ШТ-8 |
| Словарь `parent` (ru, en) | ЛК-2 |

**Условие старта.** Собраны согласия на данные детей (бумажные из MVP) и внесены семьи. В старом приложении данных о семьях и телефонах родителей нет, поэтому **все семьи вносятся с нуля**: вручную admin или при одобрении заявок родителей. Сбор контактов стоит начать ещё в MVP — вместе с бумажными согласиями (раздел 4).

### Волна 3 — голосовая проверка стихов (AI)

| Что | Спецификация |
|---|---|
| Gate: тест распознавания на 30–50 реальных записях | 6.2 |
| Согласие родителя на запись голоса | ВП-15, 3.17 |
| Запись попытки, асинхронная оценка, обратная связь ребёнку | 6.3–6.5, ВП-1…ВП-14 |
| Правило «N дней» и окно практики | ВП-8 |
| Стихи прошедших уроков | ВП-16 |
| Метрики качества AI-оценки | 9.3 |
| Достижение «Три дня со стихом» | `achievements_spec.md`, 9.1 |

**Условие старта.** Работает волна 2 (запись ведёт родитель) **и** пройден gate 6.2. Если распознавание детской речи не проходит gate — волна сводится к «ребёнок записывает, учитель слушает», без автоматической оценки.

## 4. Как MVP обходится без семей и родителей

Временные правила MVP. Их нужно снять в волне 2.

| Ситуация | В MVP | В волне 2 |
|---|---|---|
| Согласие на данные ребёнка | Только бумажное: admin отмечает на карточке ученика, кто подписал (текстом), дату, версию текста, где хранится оригинал | Подписант — взрослый семьи; плюс электронное согласие |
| Удаление данных ребёнка | Родитель обращается к admin; admin создаёт запрос от имени родителя (кто обратился, как подтвердил личность) и выполняет | Родитель создаёт и отменяет запрос сам |
| Заявка от родителя | Admin может только отклонить с причиной «доступ родителей откроется позже» или оставить заявку на рассмотрении | Одобрение с ролью parent и привязкой к семье |
| Контакты родителей для учителя | Нет: в старом приложении их тоже нет. Подписант бумажного согласия записывается текстом — телефон можно указать там же | Страница семьи, контакты взрослых, СМ-8 |
| Кирпичики | Только баллы уроков, без бонусов и штрафов | Волна 1 добавляет бонус и штрафы |
| Достижения из старого приложения | Перенесены в базу, в интерфейсе не показываются; «набрано» их бонусы не учитывает | Видны в карточке ученика; бонусы входят в «набрано» |

## 5. Схема базы данных: сразу целиком (решение владельца)

Схема Postgres создаётся одной миграцией по всей спецификации — включая таблицы post-MVP: семьи и взрослые семей, согласия всех видов, голосовые попытки, каталог и выдачи достижений с доказательствами, штрафы, режим достижений группы, дайджесты.

**Почему это разумно:** спецификация детальная, связи известны; миграция данных из старого приложения переносит выданные достижения сразу (п. С-4); не будет поздних миграций, которые меняют таблицы с живыми данными MVP.

**Правила, чтобы это не стало ловушкой:**

**С-1 Зависимости направлены от post-MVP к MVP.** Таблицы post-MVP ссылаются на таблицы MVP (выдача достижения → запись проверки; взрослый семьи → пользователь), но **не наоборот**. Код MVP никогда не обязан заполнять таблицы post-MVP.

**С-2 Ссылки из MVP на post-MVP — только необязательные.** Где MVP-таблица должна будет ссылаться на post-MVP (ученик → семья; согласие → взрослый семьи), колонка допускает пустое значение, а в MVP заполняется текстовый заменитель (например, «кто подписал» — текстом).

**С-3 Нет API и экранов для post-MVP.** Таблицы существуют, но в MVP нет серверных действий, страниц и словарей для них. Включение — флаги приложения (`features.achievements`, `features.parents`, `features.voice`), выключенные по умолчанию; роль parent недоступна при одобрении заявки, пока `features.parents` выключен.

**С-4 Миграция заполняет таблицы post-MVP заранее — там, где есть данные.** Выданные достижения из старого приложения переносятся сразу (Раздел 13 спецификации) и появятся в интерфейсе в волне 1. Семей и телефонов родителей в старом приложении нет — таблицы семей в MVP остаются пустыми.

**С-5 Схема может меняться — через обычные миграции.** «Сразу целиком» не значит «навсегда». Если волна 2 или 3 покажет, что модель нужно поправить, это делается миграцией, как обычно. Чем меньше в таблице живых данных, тем дешевле правка — поэтому таблицы post-MVP правятся легко, а таблицы MVP — осторожно.

**С-6 Два окружения: dev и prod.** Prod — пустая база: миграции, справочники (Библия, стартовый каталог достижений и штрафов), первый admin. Dev — те же миграции плюс фейковые данные из прототипа (файл фикстур, команда `seed:dev` с защитой от запуска на prod). Таблицы волн 1–3 в dev можно заполнять фейковыми данными заранее — это помогает разрабатывать и показывать; в prod они пусты до включения флагов. Подробности — Раздел 15 спецификации.

**С-7 Библия загружается скриптами.** Таблицы переводов и стихов создаются в первой миграции; тексты — скриптами владельца (русский и английский), которые запускаются отдельно от миграций и идемпотентны. До получения скриптов MVP можно разрабатывать на небольшом наборе стихов из прототипа в dev. *Скрипты и данные получены: каталог [`Bible/`](./Bible/README.md) — RST (русский) готов к загрузке; NIV (английский) собирается локально и не коммитится до решения по лицензии (12.2 п. 30).*

## 7. Открытые вопросы

1. ~~Достижения в MVP или в волне 1?~~ Решено: post-MVP (волна 1), включая ручную выдачу и штрафы. Перенесённые из старого приложения выдачи сохраняются в базе и появятся в волне 1. Учителям нужно сказать заранее, что на время между MVP и волной 1 достижения не выдаются.
2. ~~Контакты семей в MVP~~ — снят: в старом приложении нет ни семей, ни телефонов родителей, учитель ничего не теряет при переезде.
3. **Заявки родителей в MVP.** Предложено: не отклонять, а держать «на рассмотрении» до волны 2 — тогда не придётся просить людей регистрироваться заново.
4. **Срок между MVP и волной 2.** Семьи вносятся с нуля; от срока зависит, сколько admin внесёт вручную, а сколько создастся само при одобрении заявок родителей.
5. **Открытые вопросы по окружениям и Библии** — в спецификации, 12.2 пп. 29–35: общая нумерация стихов, лицензия английского перевода, первый admin, справочники в prod, один или два проекта Neon.
