## 1. Purpose

Зафиксировать решение владельца: физическая схема создаётся одной начальной миграцией по всей спецификации, включая таблицы post-MVP, и правила, при которых это безопасно.

## 2. Scope / Out of scope

**В scope:** границы MVP и post-MVP в схеме, флаги, поведение миграции.  
**Вне scope:** содержимое таблиц ([`database_schema_v1.md`](../03_data_model/database_schema_v1.md)), порядок миграции данных из старого приложения (W12-02).

## 3. Context

Спецификация детальна, связи известны; выданные достижения из старого приложения переносятся сразу (С-4). Поздние миграции таблиц с живыми данными MVP дороже, чем заранее созданные пустые таблицы. Риск: таблицы post-MVP «протекут» в MVP-код.

## 4. Decision

1. **Одна начальная миграция** создаёт схему целиком: MVP (организация, пользователи, школа, ученики, уроки, проверки, кирпичики, журналы, заявки, удаление, Библия) и волны 1–3 (достижения и штрафы, семьи, голосовые попытки и согласия).
2. **Направление зависимостей (С-1):** post-MVP → MVP. Код MVP не обязан и не должен заполнять post-MVP таблицы.
3. **Ссылки MVP → post-MVP — только `NULL`-able (С-2):** единственная — `pupil.family_id`; в MVP — `NULL`, подписант бумажного согласия хранится текстом (`child_data_consent.signer_name`).
4. **Нет API, экранов и словарей post-MVP (С-3):** серверных действий и страниц для таблиц post-MVP в MVP нет.
5. **Флаги** `features.achievements`, `features.parents`, `features.voice` в `app_setting`, по умолчанию выключены; проверяются **на сервере** (use-case отказывает), не только в UI; роль `PARENT` недоступна при одобрении заявки, пока `features.parents = false`.
6. **Миграция данных (С-4):** заполняет таблицы волны 1 там, где есть данные (выданные достижения со статусом «источник неизвестен»); таблицы семей остаются пустыми.
7. **Эволюция (С-5):** схема меняется обычными миграциями; изменение таблицы MVP требует осторожности (живые данные), post-MVP — свободнее.
8. **Окружения (С-6):** одни миграции для dev и prod; prod после развёртывания содержит схему, справочники, первого admin и больше ничего.
9. **Библия (С-7):** таблицы — в первой миграции; тексты — идемпотентными скриптами отдельно ([ADR-009](./adr_009_bible_translations_and_verse_numbering.md)).

## 5. Rejected alternatives

| Альтернатива | Почему отклонена |
|--------------|------------------|
| Поэтапные миграции по волнам | Правка таблиц с живыми данными; перенос достижений потребовал бы раннего ad-hoc хранилища |
| Отдельная схема / база для post-MVP | Нарушает транзакционные связи (проверка → достижение); лишняя операционная сложность |
| Хранить post-MVP в JSON-полях MVP-таблиц | Теряются ограничения и индексы; миграция данных хуже |
| Не создавать таблицы до старта волны | Миграция из старого приложения не сможет сохранить выданные достижения |

## 6. Consequences

- Размер и ревью начальной миграции выше; её проверяет `reviewer` как T3 (схема, S).
- Тест `PKG-03`: MVP-код не импортирует и не запрашивает таблицы post-MVP.
- Таблицы post-MVP «спят»: нет данных и экранов, но есть в схеме и в бэкапах.
- Включение волны = флаг + новые use-case и экраны + при необходимости миграция правки схемы.

## 7. Paths (H / N / S)

| Путь | Описание | Исход |
|------|----------|-------|
| **H** | `prisma migrate deploy` на пустой БД | Все таблицы §5–§6 схемы созданы; приложение стартует с выключенными флагами |
| **N** | Флаг `features.parents = false`, заявка запрашивает `PARENT` | Отклонена с причиной «доступ родителей откроется позже» |
| **N** | MVP-код пытается писать в post-MVP таблицу | Отклоняется review и тестом PKG-03 |
| **S** | Включение флага через UI | Только `ADMIN`, запись в журнале; в MVP флаги меняются только конфигурацией |
| **Drift** | Prisma schema ≠ `database_schema_v1.md` | Правка схемы начинается с документа |

## 9. Acceptance criteria

- [ ] Начальная миграция создаёт все таблицы схемы — исход: сверка списка таблиц с §5–§6 схемы.
- [ ] MVP-таблицы не имеют обязательных FK на post-MVP — исход: проверка FK скриптом.
- [ ] Флаги выключены по умолчанию и проверяются на сервере — исход: тест use-case.
- [ ] В MVP нет маршрутов и словарей post-MVP — исход: сверка с `canonical_routes.md` §4 и `messages/`.
