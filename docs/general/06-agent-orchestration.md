# Оркестрация AI-агентов: контекст, роли, выбор моделей

**Тип:** учебное руководство (deep dive)
**Для кого:** владелец проекта, который хочет понимать, что происходит «под капотом» при автоматической реализации фазы
**Операционный канон:** [`docs/guidelines/agent-phase-orchestration.md`](../guidelines/agent-phase-orchestration.md) (переносимый), [`docs/meta/ai_agent_model_routing.md`](../meta/ai_agent_model_routing.md) § Phase driver, `.cursor/rules/model-routing.mdc`, `agent-commit-pipeline.mdc`, `agent-code-review-subagent.mdc`. При расхождении правы они, а не этот текст.

Документ объясняет **почему** pipeline устроен так, а не иначе. Сначала идут общие принципы, верные для любой LLM. Затем особенности Claude и пары Grok / Composer. В конце разобран pipeline Sunday School шаг за шагом.

## Часть I. Основы

### 1. Что такое агент

LLM сама по себе — функция «текст на входе → текст на выходе». Она ничего не помнит между вызовами. **Агент** — это цикл вокруг неё:

```text
┌─────────────────────────────────────────────────────────┐
│ контекст = системный промпт + правила + история диалога │
│                     │                                   │
│                     ▼                                   │
│          LLM генерирует ответ                           │
│                     │                                   │
│       есть вызов инструмента? ──нет──► конец хода       │
│                     │да                                 │
│                     ▼                                   │
│   harness выполняет инструмент (Read, Bash, Edit…)      │
│                     │                                   │
│   результат ДОПИСЫВАЕТСЯ в контекст ──► снова LLM       │
└─────────────────────────────────────────────────────────┘
```

Ключевое следствие: **каждый шаг цикла заново отправляет модели весь накопленный контекст**. Агент «помнит» только то, что лежит в окне. Всё прочитанное (файлы, логи, diff) остаётся там до конца сеанса и оплачивается на каждом следующем шаге.

**Harness** — программа, которая крутит этот цикл: Claude Code, Cursor Agent, Codex CLI и т. п. Она решает, какие инструменты доступны, что спрашивать у человека (permissions), как запускать субагентов и что делать при переполнении.

### 2. Контекстное окно: из чего состоит

Окно — это всё, что модель видит в момент генерации. В типичном сеансе Claude Code или Cursor оно состоит из следующих слоёв:

| Слой | Когда попадает | Пример в этом проекте |
|------|----------------|------------------------|
| Системный промпт harness | Всегда, в начале | Инструкции Claude Code / Cursor |
| Схемы инструментов | Всегда | Описания Read, Bash, Agent, MCP-инструментов. Десятки MCP-инструментов могут занять тысячи токенов |
| Проектные инструкции | Всегда | `CLAUDE.md` → `AGENTS.md`, `.claude/rules/*.md` без `paths` |
| Правила по пути | Когда агент трогает подходящий файл | `.claude/rules/*.md` с `paths:` (UI-правила для `apps/web/**`) |
| Сообщения пользователя | По ходу | Фраза запуска фазы |
| Ответы модели и **reasoning** | По ходу | Рассуждения (thinking), план, текст |
| **Результаты инструментов** | По ходу | Прочитанные файлы, вывод `npm`, `git diff` |

**Измерение на нашем репозитории.** Постоянно активные правила без `paths:` весят около 72 КБ, `CLAUDE.md` + `AGENTS.md` ещё около 25 КБ. Кириллица токенизируется плотнее латиницы (грубо 2–3 символа на токен против ~4), поэтому это **порядка 30–45 тыс. токенов** ещё до того, как агент прочёл первую строку задачи. Цифра ориентировочная. Точная зависит от токенизатора конкретной модели.

Отсюда первый практический вывод: **always-on правила — налог на каждый сеанс и каждый субагент**. Драйвер фазы открывает свежий сеанс на каждый CU, и каждый из них платит этот налог заново. Поэтому правила нужно держать лаконичными и по возможности ограничивать `paths`/`globs`.

### 3. Экономика токенов

Общие принципы для всех провайдеров:

1. **Входные токены оплачиваются на каждом шаге цикла.** Сеанс из 40 шагов с контекстом 80k токенов — это не 80k, а сумма контекстов всех шагов, то есть миллионы входных токенов. Без кэша это было бы непомерно дорого.
2. **Prompt caching.** Провайдеры кэшируют неизменный **префикс** контекста. Повторное чтение префикса стоит заметно дешевле свежего ввода. Harness кэширует автоматически, но это работает, только пока префикс стабилен. Порядок в окне: системный промпт → инструменты → правила → история. Изменение в начале (например, правка always-on правила посреди сеанса) инвалидирует кэш всего, что после него. У Claude кэш живёт ограниченное время (минуты или час в зависимости от настройки), и долгая пауза делает следующий шаг «холодным».
3. **Выходные токены дороже входных** в несколько раз. Это касается и reasoning / thinking: глубокое рассуждение на каждый шаг — главный множитель стоимости у reasoning-моделей.
4. **Длинный контекст дороже за токен.** У ряда моделей и тарифов выше порога (например 200k) цена за токен растёт. У Grok 4.7 она удваивается, это записано в `model-routing.mdc` §5.

Актуальные цены берите только со страниц провайдеров (Anthropic, xAI, Cursor). Цены меняются, а запомненные цифры устаревают.

### 4. Качество деградирует раньше, чем кончается окно

Окно в 200k или 1M токенов не означает, что модель одинаково хорошо работает на всём объёме. Наблюдаемые эффекты:

- **Context rot / размывание.** Чем больше нерелевантного текста, тем хуже модель следует конкретным инструкциям. Правило из начала окна «забывается» под 100k токенов логов.
- **Lost in the middle.** Информация в середине длинного контекста извлекается хуже, чем в начале и в конце.
- **Самоподкрепление ошибок.** Неудачная попытка остаётся в истории, и модель склонна повторять уже выбранный путь. Поэтому эскалационная лестница говорит: одна повторная попытка, затем смена подхода (architect), затем стоп.
- **Компакция с потерями.** Когда окно заполняется, harness сжимает историю в резюме (auto-compact). Детали — точные пути, номера строк, тексты ошибок — пропадают.

**Вывод:** бороться нужно не с переполнением, а с **засорением**. Цель — чтобы в окне всегда был только материал текущего шага.

## Часть II. Как агенты взаимодействуют

### 5. Механизмы делегирования

| Механизм | Контекст | Что возвращает родителю | Стоимость | Когда |
|----------|----------|--------------------------|-----------|-------|
| **Инструмент** (Read, Bash) | Общий с агентом | Весь вывод | Дёшево, но засоряет | Короткие, нужные целиком результаты |
| **Скрипт с хвостом лога** | Нет LLM | Код выхода + ~40 строк | Почти ноль токенов | Детерминированная работа: проверки, git |
| **Субагент** (Agent / Task tool) | Свежий, отдельный | Только финальное сообщение | Холодный старт: системный промпт + правила + чтение файлов заново | Изоляция шума, независимый взгляд (review), другая модель |
| **Свежий сеанс** (`claude -p`, новый чат) | Полностью новый | Ничего, кроме файлов и git | Холодный старт | Граница крупной единицы работы (CU) |
| **Компакция** | Тот же, сжатый | n/a | Один вызов на резюме | Аварийно, когда иначе нельзя |
| **Skill** | Тот же | Инструкции загружаются по требованию | Тело skill только при вызове | Редко нужные процедуры: не держать их always-on |
| **Hook** | Нет LLM | Блок/сообщение | Ноль токенов, если прошёл | Обязательные проверки, которые нельзя забыть |

**Главная асимметрия субагента:** внутри он может прочитать 100k токенов, а родителю вернёт 15 строк. Это единственный способ «прочитать много», не засоряя основной контекст. Но у субагента нет памяти родителя: всё, что ему нужно, должно быть в промпте или в файлах, которые он прочтёт сам. Поэтому промпт `reviewer` — это указатель («CU такой-то, задачи там-то, читай `git diff --staged`»), а не пересказ.

**Ограничение вложенности.** В Claude Code субагент не может запускать своих субагентов. Схема «оркестратор фазы → оркестратор CU → Grok-субагент» там не реализуема. Поэтому у нас главный агент сеанса CU сам вызывает `architect` / `reviewer`, а «оркестратор фазы» — не LLM, а скрипт.

### 6. Внешнее состояние вместо памяти

Если контекст обнуляется между CU, где хранится прогресс? В файлах и git:

| Состояние | Где |
|-----------|-----|
| Какие CU сделаны | Чекбоксы `- [x]` в `P{N}_tasks.md` |
| Что сделано | Коммиты (subject = заголовок CU) |
| Логи проверок | `.local/phase-runs/*.log` |
| Список путей для коммита | `.local/phase-runs/<CU>.paths` |
| Отложенные ручные проверки | `.local/phase-runs/P{N}-smoke.md` |

Такой подход делает систему **возобновляемой**. Упал CU5 — человек чинит причину и перезапускает драйвер, а тот сам находит первый незакрытый CU. Ничего «помнить» не нужно.

### 7. Детерминизм против LLM

Правило большого пальца: **если результат шага однозначно определён входом, LLM там не нужна.**

| Шаг | LLM? | Почему |
|-----|------|--------|
| Выбрать следующий CU | Нет | Первый незакрытый в файле: это парсинг |
| Запустить lint/test/typecheck | Нет | Команда известна заранее |
| Собрать сообщение коммита | Нет | `ветка + subject из заголовка` |
| Проверить, что в индексе только нужные файлы | Нет | Сравнение множеств |
| Написать код по задаче | **Да** | Творческая работа |
| Понять, удовлетворяет ли diff задаче | **Да** | Суждение |
| Решить, что спека противоречива | **Да** | Суждение |

Каждый LLM-шаг дорог, медленен и **вероятностен**: он может пропустить флаг, перепутать порядок, «улучшить» сообщение коммита. Скрипт делает одно и то же каждый раз и возвращает код выхода, на который можно опереться.

## Часть III. Борьба с переполнением контекста

### 8. Стратегии по убыванию эффективности

1. **Не впускать.** Читать раздел `§4.2`, а не весь PRD. Читать `git diff --stat`, а не весь diff. Не перечитывать уже прочитанное.
2. **Вынести в файл.** Полный лог — в `.local/phase-runs/`, в контекст — хвост. Длинный план — в `.cursor/plans/*.md`, в контекст — путь.
3. **Изолировать.** Шумное чтение (разведка кодовой базы, review diff) — в субагенте. Обратно 15 строк.
4. **Сбросить.** Новый сеанс на границе естественной единицы работы (CU). Состояние — в файлах.
5. **Ограничить.** `--max-turns`, бюджет токенов на сеанс, лимит ответа субагента.
6. **Сжать (последнее средство).** `/compact` или авто-компакция. Работает, но теряет детали. Если это случается регулярно, единица работы слишком крупная.

### 9. Кто сколько вносит в нашем pipeline

Оценки порядка величин для одного CU среднего размера. Это **иллюстрация пропорций, не измерение**.

| Участник | Своё окно | Что попадает в окно сеанса CU |
|----------|-----------|-------------------------------|
| Always-on правила + системный промпт | — | ~30–50k (постоянный налог, кэшируется) |
| Чтение задачи CU + `§`-разделов | — | ~5–15k |
| Чтение и правка исходников | — | ~10–40k |
| `cu-verify.mjs` (зелёный) | Нет LLM | 2 строки |
| `cu-verify.mjs` (красный) | Нет LLM | ~40 строк хвоста |
| `cu-commit.mjs` | Нет LLM | Список путей / хеш + хвост хука |
| `architect` (если вызван) | ~50–100k своих | ≤ 15 строк |
| `reviewer` (если вызван) | ~50–120k своих (правила + задача + diff) | ≤ 15 строк |
| Следующий CU | Новый сеанс | **0** от предыдущего |

Для сравнения — исходный сценарий «один чат на всю фазу, сырой `git commit`, review в том же контексте». Только вывод `next build` из хука — это тысячи строк. Diff плюс разбор review — десятки тысяч токенов. Через 3–4 CU окно переходит за 150–200k, начинается деградация, а Grok выше 200k тарифицируется вдвое.

### 10. Антипаттерны

| Антипаттерн | Почему плохо | Что делать |
|-------------|--------------|------------|
| «Прочитай всю документацию фазы» | Десятки тысяч токенов, из которых нужна десятая часть | Только `§`, указанные в задаче |
| Агент запускает `npm run build` сам | Тысячи строк вывода в окне | Хук + хвост лога |
| Субагент возвращает «подробный отчёт» | Шум переезжает из его окна в родительское | Жёсткий лимит ≤ 15 строк и формат |
| Пересказывать субагенту историю чата | Стоит токенов, и субагент теряет независимость | Указатель на файлы |
| «Оркестратор оркестраторов» на LLM | Каждый уровень — холодный старт и пересказ | Скрипт-драйвер |
| Правило `alwaysApply` для узкой темы | Налог на все сеансы | `paths` / `globs` или skill |
| Цикл «исправь → проверь» без лимита | Сжигает токены, самоподкрепляет ошибку | Один повтор → architect → стоп |

## Часть IV. Выбор модели

### 11. Общие принципы (для любых провайдеров)

Выбирайте модель по четырём осям:

1. **Цена ошибки.** Ошибка в спеке или плане размножается во все последующие шаги, ошибка в одной функции — нет. Чем выше по течению решение, тем сильнее нужна модель.
2. **Тип работы.** Генерация кода по ясной спеке — «ремесло». Поиск противоречий, архитектура, review рисков — «суждение».
3. **Объём контекста.** Много читать и мало решать (поиск) может быстрая дешёвая модель. Много решать на малом объёме — сильная модель.
4. **Частота.** Шаг, который выполняется 50 раз за фазу, должен быть дешёвым. Шаг, который выполняется раз за фазу, может быть дорогим.

Классы моделей (имена меняются, классы остаются):

| Класс | Характер | Типичные задачи |
|-------|----------|-----------------|
| **Frontier reasoning** | Самые точные, медленные, дорогие; режимы усиленного рассуждения | Спека, архитектура, review рисков, диагностика неочевидного бага |
| **Workhorse coding** | Хороший код, хорошо следует инструкциям, умеренная цена | Реализация задач по готовой спеке, большинство шагов агента |
| **Fast / small** | Быстрые и дешёвые, слабее в многошаговом рассуждении | Поиск по кодовой базе, классификация, суммаризация, простые правки |

**Effort / thinking.** Многие модели дают регулировать глубину рассуждения. Высокое усилие оправдано там, где думают (`architect`, `reviewer`), и расточительно там, где пишут по спеке. Наш `model-routing.mdc` §5 запрещает `xhigh`, fast-варианты и 500k-контекст без явной просьбы.

**Независимость ревьюера.** Review той же моделью в том же контексте почти бесполезен: модель видит свой замысел, а не код. Минимум — свежий контекст (субагент). Лучше — другая модель или семейство: ошибки разных моделей коррелируют слабее. Поэтому в Cursor код пишет Composer, а проверяет Grok.

### 12. Модели Claude

Семейство Claude 5 (актуальные ID — в документации Anthropic):

| Модель | Класс | Роль в нашей схеме |
|--------|-------|-------------------|
| **Opus 5.5** (`claude-opus-5-5`) | Frontier reasoning | `architect`, `reviewer`: туда `rules:sync` отображает Grok |
| **Sonnet 5.5** (`claude-sonnet-5-5`) | Workhorse coding | Сеанс CU, `implementer`: туда отображается Composer |
| **Haiku 5.5** (`claude-haiku-5-5`) | Fast / small | Встроенный Explore / поиск, массовые простые проверки |
| **Fable 5.1** (`claude-fable-5-1`) | См. описание Anthropic | В pipeline не задействована |

Особенности, важные для оркестрации:

- **Extended thinking / effort.** Opus и Sonnet поддерживают регулируемую глубину рассуждения. Thinking-токены оплачиваются как выходные. Для `reviewer` глубина окупается, для механической правки — нет.
- **Prompt caching.** Работает автоматически в Claude Code. Отсюда практическое правило: не правьте always-on правила и `CLAUDE.md` посреди прогона фазы, иначе каждый следующий шаг пойдёт «холодным».
- **Субагенты Claude Code.** Определяются файлами `.claude/agents/*.md` с полями `model` и `tools`. У нас они генерируются `npm run rules:sync` из `.cursor/agents/*.md`: `grok` → `opus`, `composer` → `sonnet`, `readonly` → только Read/Grep/Glob/Bash. Вложенные субагенты не поддерживаются.
- **Headless.** `claude -p` выполняет один сеанс без интерактива. Полезные флаги: `--model`, `--max-turns`, `--output-format json` (отчёт об использовании токенов и стоимости), `--allowedTools`. Без настроенного allowlist headless-сеанс не может спросить разрешения, и вызов инструмента падает.
- **Большие окна.** У части моделей есть варианты с окном до 1M токенов. Это страховка, а не стратегия: качество и цена на таком объёме хуже, чем у свежего сеанса с правильными 50k.
- **`/compact`, `/clear`.** Ручная компакция и сброс в интерактивном сеансе. В драйвере не нужны: сброс делает сам драйвер.

### 13. Grok и Composer (Cursor)

| Модель | Класс | Роль |
|--------|-------|------|
| **Grok 4.7** (`effort=high`, не fast) | Frontier reasoning | `architect`, `reviewer`, Phase DoR audit на профилях выше `lean` |
| **Composer 2.5** (не fast) | Workhorse coding | Оркестратор (чат), `implementer` |
| Встроенный Explore | Fast | Поиск |

Особенности: модель субагента задаётся во frontmatter `.cursor/agents/*.md`, а не фразой в промпте. Fast-варианты быстрее, но дороже и не нужны в фоне. У Grok 4.7 цена удваивается за 200k токенов. В Cursor нет штатного headless-аналога `claude -p`, поэтому драйвер в режиме `print` выдаёт промпт, а свежий Agent-чат открывается на каждый CU.

### 14. Сводная таблица «задача → модель»

| Задача | Класс | Claude | Cursor | Почему |
|--------|-------|--------|--------|--------|
| Phase DoR audit / spec-gap | Frontier | Opus | Grok 4.7 high | Ошибка размножается по всей фазе |

## Часть V. Pipeline Sunday School

### 15. Эволюция решения

Полезно видеть, как схема пришла к текущему виду: каждое изменение закрывает конкретную проблему.

| Версия | Идея | Проблема |
|--------|------|----------|
| 0. Исходная | Grok планирует; на каждый CU свой Composer-оркестратор; Grok-субагент для сложного; отдельный Composer для коммита | Вложенность субагентов (в Claude Code невозможна); холодные старты на каждом уровне; «подтверждаю» не устранено |
| 1. Grok v1 | Один Composer-оркестратор на фазу; отдельные LLM-субагенты для проверки и коммита | Контекст копится по фазе; review читает staged diff до того, как что-то застейджено; двойной `next build`; permission-промпты не решены |
| 2. Ревизия | Скрипты вместо LLM для механики; свежий сеанс на CU; allowlist | — |
| 3. Сверка с профилем | `lean`: `reviewer` только для T3/S, DoR inline, без итогового review ветки; `Smoke: deferred/blocking`; коммит только через скрипт | — |

Урок: **первые версии добавляли агентов, финальная убрала их там, где нужна не мысль, а процедура.**

### 16. Анатомия прогона одного CU

```text
run-phase.mjs  (скрипт, 0 токенов)
  │ 1. parseCommitUnits → первый CU без всех [x]
  │ 2. git status → грязь вне Files CU? → exit 1
  │ 3. пишет P01-CU7.paths, рендерит промпт
  ▼
claude -p  (Sonnet / Composer, свежее окно)
  │ ~30–50k  always-on правила (кэш)
  │ ~5–15k   строки CU + §-разделы
  │ ~10–40k  исходники и правки
  │ ─ DoR провален? → architect (Opus/Grok): своё окно, назад ≤15 строк
  │ ─ ставит [x], пишет paths-файл
  │ ─ cu-verify --full ───────► lint, test, typecheck → лог; назад 2 строки
  │ ─ cu-commit stage ────────► git add -- <paths>
  │ ─ reviewer (Opus/Grok) ───► своё окно: правила + задачи + diff; назад ≤15 строк
  │      blocker? → правка → stage → review дельты (1 раз) → иначе exit≠0
  │ ─ cu-commit commit ───────► хук: rules:check, lint-staged, typecheck, next build
  │                              назад: хеш + хвост
  ▼ сеанс завершён, окно выброшено
run-phase.mjs: CU отмечен? → следующий CU
```

### 17. Почему каждое решение именно такое

| Решение | Альтернатива | Почему выбрано |
|---------|--------------|----------------|
| Свежий сеанс на CU | Один чат на фазу | Окно не растёт; кэш правил всё равно переиспользуется между сеансами в пределах TTL |
| Драйвер — скрипт | LLM-оркестратор фазы | Выбор следующего CU — парсинг; скрипт не устаёт и не галлюцинирует |
| Состояние в чекбоксах | Память чата | Возобновляемость после любого сбоя |
| `cu-verify` без `build:check` | Полная проверка до коммита | Хук всё равно соберёт; двойной `next build` — минуты и тысячи строк |
| `typecheck` только с `--full` | Всегда | Нужен лишь перед дорогим `reviewer`, чтобы тот не разбирал красный код; на diff-only его делает хук |
| Stage до review | Stage в момент коммита | `reviewer` читает `git diff --staged`; иначе ему нечего смотреть |
| Индекс = списку путей | `git add .` | В коммит не попадут чужие файлы и секреты; проверяется механически |
| Сообщение коммита собирает скрипт | Модель пишет сама | Формат commitlint гарантирован; модель передаёт только subject |
| `reviewer` только для T3/S (`lean`) | На каждый runtime-CU | Профиль качества: дорогой гейт там, где риск |
| Ответы субагентов ≤ 15 строк | Подробные отчёты | Шум не переезжает в родительское окно |
| Allowlist на скрипты, deny на сырой git | Разрешить `git commit` | Префиксное правило пропустит `--amend`/`--no-verify` |
| `Smoke: deferred` | Стоп на каждом ручном smoke | Человек проверяет пачкой в конце фазы |

### 18. Где остаётся человек

| Событие | Почему автомат не решает сам |
|---------|------------------------------|
| Запуск фазы | Осознанное решение потратить ресурсы и разрешить коммиты |
| Blocking Open question | Продуктовое решение, а не техническое |
| Blocker после review дельты | Две модели разошлись во мнении; цикл дальше дорог и опасен |
| Повторный провал после правки спеки | Проблема глубже, чем видит агент |
| `Smoke: blocking` | Нужна проверка руками в реальном окружении (Telegram, браузер) |
| Конец фазы: smoke, push, PR | Публикация — необратимое внешнее действие |

### 19. Безопасность автономного прогона

- **Принцип наименьших прав.** Allowlist содержит только скрипты и read-only git. Push, сырой commit/add, `reset --hard`, чтение и правка `.env*` запрещены.
- **Скрипт как граница доверия.** `cu-commit.mjs` сам отвергает `--amend`, `--no-verify`, `push`, пути вне репозитория и секретные файлы. Даже ошибающийся агент не сможет их передать.
- **Хуки нельзя обойти.** `--no-verify` запрещён правилом, deny-списком и скриптом — три независимых слоя.
- **Prompt injection.** Агент читает файлы, логи и, возможно, внешние документы (Context7). Текст в них — данные, а не команды. Узкий allowlist ограничивает ущерб, если агент всё-таки «поверит» инструкции из файла.
- **Ничего не уходит наружу.** Коммиты локальные, push делает человек.

## Часть VI. Практика

### 20. Как читать расход после прогона

- `claude -p --output-format json` возвращает usage по сеансу: входные, кэшированные и выходные токены. Сравните CU между собой: выброс почти всегда означает лишнее чтение или цикл исправлений.
- Логи `.local/phase-runs/verify-*.log` показывают, сколько раз падали проверки.
- Высокая доля некэшированного ввода говорит о том, что префикс менялся (правились правила) или были долгие паузы.

### 21. Чек-лист перед запуском фазы

- [ ] В `P{N}_tasks.md` у каждого CU корректный заголовок: subject, `Review:`, `Smoke:`
- [ ] DoR проверен (на `lean` — inline; открытых блокирующих вопросов нет)
- [ ] Дерево чистое (`git status`)
- [ ] Allowlist настроен; headless-сеанс не упрётся в permission
- [ ] Модель сеанса задана явно (`--model`), не унаследована от последнего выбора
- [ ] Драйвер запускается из терминала (не из агентского Bash с 10-минутным таймаутом)
- [ ] Always-on правила не будут меняться во время прогона

### 23. Глоссарий

| Термин | Значение |
|--------|----------|
| Агент | Цикл «LLM ↔ инструменты» под управлением harness |
| Harness | Программа, исполняющая цикл агента (Claude Code, Cursor) |
| Контекстное окно | Весь текст, который модель видит при генерации |
| Холодный старт | Новый контекст, который заново грузит промпт, правила и файлы |
| Prompt caching | Удешевлённое повторное чтение неизменного префикса контекста |
| Компакция | Сжатие истории в резюме с потерей деталей |
| Субагент | Агент со своим окном, вызванный другим агентом; возвращает только итог |
| Headless | Запуск сеанса без интерактива (`claude -p`) |
| CU | Commit unit — одна логическая единица работы и коммита |
| DoR | Definition of Ready — готовность задачи к реализации |
| Драйвер | Скрипт, который ведёт фазу по CU |
| Allowlist | Список действий, разрешённых без подтверждения человека |
