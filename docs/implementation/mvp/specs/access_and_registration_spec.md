## 1. Purpose

Описать экраны и поток «первый вход → регистрация → заявка → ожидание → доступ», профиль пользователя (ФИО, способы входа, удаление) и публичный текст согласия. Читают: исполнитель P01 (auth, регистрация), `reviewer` (T3), тестировщик smoke.

## 2. Scope / Out of scope

**В scope:** `/login`, `/register`, `/pending`, `/privacy`, `/profile`; режим повторного согласия; первый вход admin.  
**Вне scope:** экран «Заявки» и «Пользователи» для admin (`/approvals`, `/users` — контракт W8-03, spec на lean не требуется); механика Auth.js ([`auth_runtime_spec.md`](../../../prds/05_runtime/auth_runtime_spec.md)); электронное согласие по ребёнку и семьи (post-MVP).

## 4. Маршруты

| Маршрут | Группа | Доступ (статус) | Оболочка | Назначение |
|---------|--------|-----------------|----------|------------|
| `/login` | `(auth)` | нет сессии | нет | Вход Telegram; email + пароль (администратор) |
| `/privacy` | `(auth)` | все, без сессии | нет | Текст согласия (публичный) |
| `/register` | `(auth)` | `REGISTRATION`; режим «исправить» — `REJECTED`; режим «подтвердить согласие» — `ACTIVE` с устаревшей версией | нет | ФИО и согласие |
| `/pending` | `(auth)` | `REQUEST_PENDING`, `REJECTED` | нет | Ожидание решения |
| `/profile` | `(app)` для `ACTIVE`; `(auth)`-вид для `REQUEST_PENDING`/`REJECTED` | `REQUEST_PENDING`, `REJECTED`, `ACTIVE` | `ACTIVE` — с оболочкой; иначе без | ФИО, способы входа, удаление |

Перенаправления между статусами — [`authorization_matrix.md`](../../../prds/04_authorization_privacy/authorization_matrix.md) §6. `REGISTRATION` на любой адрес → `/register` (РГ-1).

## 5. Поток

```
Нет сессии → /login → (Telegram | email + пароль администратора) → Auth.js callback
  → пользователь не найден → создан REGISTRATION → /register
  → REGISTRATION: форма ФИО + согласие → submitRegistration → REQUEST_PENDING → /pending
  → admin: approveRequest → ACTIVE → домашний маршрут (при следующем входе/обновлении)
  → admin: rejectRequest → REJECTED → /pending (причина) → /register (исправить) → resubmit
Первый admin: `db:seed:admin` → вход по email и паролю → ACTIVE+ADMIN → /register (режим «подтвердить согласие») → /school
```

После одобрения пользователь, остававшийся на `/pending`, получает перенаправление при следующем обращении к серверу; опрос / WebSocket в MVP нет (Q-02).

## 6. Экран `/login`

| Элемент | Правило |
|---------|---------|
| Контент | Логотип, заголовок «Вход в приложение», краткое пояснение, кнопка «Войти через Telegram» (основная, 48 px, иконка), примечание «Пароль нужен только администратору» под Telegram; блок **«Вход для администратора»** (email + пароль + «Войти») **свёрнут по умолчанию** — раскрывается control с тем же заголовком; после раскрытия — разделитель «или», поля и submit; control «Скрыть» сворачивает блок; ошибка «Неверный email или пароль» (одинаково для обоих) и «Слишком много попыток — повторите через 15 минут» показываются **внутри раскрытого блока**; при `?error=` с этими кодами или после неудачного submit credentials блок **открыт**; OAuth/прочие ошибки — баннер над Telegram; ссылка «Согласие на обработку данных» → `/privacy` |
| Действие | **Клиентский** `signIn("telegram", { callbackUrl })` и `signIn("credentials", { email, password, redirect: false })` из `next-auth/react`; серверный `signIn` не используется (TG-1) |
| `callbackUrl` | только маршрут из `canonical_routes` (по умолчанию `/`) |
| Состояния | кнопки блокируются на время перехода (`aria-busy`, «Переходим…»); повторное нажатие невозможно |
| Ошибки `?error=` | блок над кнопками (`role="alert"`, иконка + текст), ключи — [`auth_runtime_spec.md`](../../../prds/05_runtime/auth_runtime_spec.md) §8: `cancelled` («Вход отменён. Можно повторить»), `account_conflict`, `denied`, `failed`; без токенов и деталей |
| Авторизованный пользователь | перенаправление по статусу, форма не показывается |
| Предупреждение dev | в `APP_ENV=dev` подпись «Тестовое окружение» (не в prod) |

## 7. Экран `/register`

### 7.1 Режимы

| Режим | Условие | Заголовок | Дополнительно |
|-------|---------|-----------|----------------|
| Новая регистрация | `REGISTRATION` | «Регистрация» | поля пусты или предзаполнены из провайдера |
| Исправление | `REJECTED` | «Исправьте данные» | сверху блок с причиной отказа (`danger-soft` фон, иконка `danger`, текст `ink`), кнопка «Отправить снова» |
| Подтверждение согласия | `ACTIVE`, версия согласия устарела (РГ-5) | «Обновилось согласие» | поля ФИО скрыты; только текст и чекбокс; после подтверждения — домашний маршрут; без подтверждения оболочка недоступна |

### 7.2 Содержание формы

| Блок | Содержимое |
|------|------------|
| Шаг 1 «Ваши данные» | Фамилия, Имя (обязательно), Отчество (необязательно); предзаполнение: Telegram — имя (из `name`), для администратора — пусто; `autocomplete` `family-name`, `given-name`, `additional-name` |
| Шаг 2 «Согласие» | краткий список: какие данные, зачем, кто оператор, как удалить (4 пункта по РГ-2); раскрываемый полный текст с версией; ссылка на `/privacy`; **чекбокс не отмечен по умолчанию**; пояснение «Это согласие не относится к данным детей» |
| Ошибка | `role="alert"` под блоками (UX-06 F3–F4) |
| Действия | «Выйти» (ghost, слева/ниже на мобильном), «Отправить заявку» (primary, `disabled`, пока не отмечено согласие) |

### 7.3 Валидация (UX-06 §5)

| Поле | Правило | Ключ сообщения |
|------|---------|----------------|
| Фамилия, имя | обязательны; буквы, пробел, дефис, апостроф; 1–50 | `auth.register.err_name`, `auth.register.err_chars` |
| Отчество | необязательно; те же символы; ≤ 50 | `auth.register.err_chars` |
| Согласие | отмечено | `auth.register.consent_required` |

Серверные коды — `VALIDATION` с `fields`, `ACCESS_ALREADY_PENDING`, `ACCESS_STATUS_INVALID` ([`access_requests_and_roles_contract.md`](../contracts/access_requests_and_roles_contract.md) §6). Введённое сохраняется при ошибке (F6).

### 7.4 Результат

| Исход | Переход |
|-------|---------|
| Успех | `/pending`, toast «Заявка отправлена» (через query-параметр и `router.replace`, `ui-toast-mutations`) |
| `ACCESS_ALREADY_PENDING` | `/pending` без ошибки (идемпотентно) |
| Версия согласия устарела между открытием и отправкой | страница обновляется с новым текстом, согласие снимается |

## 8. Экран `/pending`

| Вариант | Содержимое | Действия |
|---------|------------|----------|
| `REQUEST_PENDING` | «Заявка на рассмотрении», ФИО, дата отправки; список шагов: вход выполнен (способ), согласие (версия, дата), «Администратор рассматривает», «После одобрения откроется работа»; если есть открытый запрос на удаление — предупреждение с датой | «Профиль», «Выйти» |
| `REJECTED` | «Заявка отклонена», причина (текст admin), дата и кто решил (обезличено при удалении) | «Исправить и отправить снова» → `/register`, «Профиль», «Выйти» |

Страница **не** самообновляется; кнопка «Проверить статус» — перезапрос (SHOULD). Admin-подсказка «напомнить» (в прототипе) в MVP **не реализуется** (нет уведомлений).

## 9. Экран `/profile`

| Блок | Содержимое | Операции |
|------|------------|----------|
| ФИО | Фамилия, Имя, Отчество; «Роли: …» или «Статус: …»; язык интерфейса (только чтение, задаёт admin) | `updateOwnName` |
| Способы входа | список: Telegram («подключён» — значение `@username` · телефон, если переданы) и «Email и пароль» (только у администратора; пароль задаёт оператор — подключить/отключить нельзя); «не подключён» + «Подключить» у Telegram; «Отключить» у подключённого (если он не единственный) | `startLinkProvider` + клиентский `signIn(provider, { callbackUrl: "/profile" })`; `unlinkProvider` |
| Согласие | «Версия <версия> от <дата>» (чтение) | — |
| Удаление данных | описание «что будет удалено / обезличено» (УД-2); кнопка «Запросить удаление»; при открытом запросе — карточка статуса, срок, «Отменить запрос» | `createDeletionRequest`, `cancelRequest` |
| Выход | кнопка «Выйти» | `signOut` |

Особенности:

1. **Привязка**: если провайдер уже у этого пользователя — действие скрыто; конфликт (`AUTH_LINK_CONFLICT`) → сообщение «Этот аккаунт уже используется другим пользователем. Обратитесь к администратору для объединения» без деталей.
2. **Отвязка** — диалог подтверждения; последний способ — кнопка недоступна, подпись «Единственный способ входа» (`AUTH_LAST_IDENTITY` на сервере).
3. **Запрос на удаление** — диалог: список удаляемого и обезличиваемого (УД-7), предупреждение «Действие необратимо после выполнения»; причина необязательна; кнопка `danger`, фокус на «Отмена».
4. Для `REQUEST_PENDING` / `REJECTED` профиль рендерится без оболочки с кнопками «Назад» и «Выйти».

## 12. Happy path

| Сценарий | Результат |
|----------|-----------|
| Новый учитель входит через Telegram, заполняет ФИО, отмечает согласие | Заявка создана, `/pending`; admin одобряет; при следующем заходе — `/today` |
| Teacher привязывает Telegram в профиле | «Подключено»; повтор — идемпотентно |
| Отклонённый пользователь исправляет ФИО и отправляет снова | Новая заявка `PENDING`, `/pending` |
| Пользователь запрашивает удаление и отменяет | Запрос `CANCELLED`, данные не тронуты |
| Первый admin входит по `FIRST_ADMIN_EMAIL` | `ACTIVE`+`ADMIN`, экран согласия, затем `/school` |

## 13. Negative paths

| Случай | Исход |
|--------|-------|
| Отказ у провайдера (cancel) | `/login?error=…`, сообщение «Вход отменён», повтор возможен |
| `DISABLED` / `DELETED` входит | `/login` с «denied», причина не раскрывается |
| Согласие не отмечено | Кнопка неактивна; сервер при обходе — `VALIDATION` |
| Двойная отправка регистрации | Кнопка блокируется; повтор идемпотентен |
| Истёкшая `REGISTRATION` (> 30 дней) | При входе запись очищается и создаётся заново, пользователь видит `/register` |
| Привязка чужого Telegram id | `AUTH_LINK_CONFLICT`: сообщение без деталей |
| Отвязка последнего способа | Недоступна |
| Второй открытый запрос на удаление | Показывается существующий |
| Сессия оборвалась на форме | Отправка → `/login`; введённое теряется (в MVP, Q-03) |

## 14. Security paths

| Путь | Требование | AZ / ссылка |
|------|------------|-------------|
| S-1 | `userId` берётся из сессии; клиент не передаёт идентификаторы пользователей | AZ-D5, auth_runtime_spec §10 |
| S-2 | `callbackUrl` — только маршруты из `canonical_routes`, без внешних хостов | auth_runtime_spec §5.4 |
| S-3 | В URL нет ФИО, email, причин; только маркеры статуса и `error` | UX-06 F11 |
| S-4 | `FIRST_ADMIN_EMAIL` и значения `providerAccountId` не отображаются клиенту | ADR-003 §5 |
| S-5 | Серверная валидация ФИО и согласия независимо от клиента | UX-06 F2 |
| S-6 | Сообщения ошибок входа без токенов, JWKS, stack | auth_runtime_spec §8 |
| S-7 | Профиль пользователя доступен только владельцу; чужой — через `/users/[userId]` у admin | AZ-02, AZ-05 |

## 15. Requirements

| ID | MUST / SHOULD |
|----|---------------|
| R-1 | MUST: вход — клиентский `signIn`; серверный `signIn` не вызывается |
| R-2 | MUST: чекбокс согласия не отмечен по умолчанию; кнопка отправки неактивна без него |
| R-3 | MUST: «Выйти» присутствует на `/register` и `/pending` |
| R-4 | MUST: сообщения ошибок входа — по ключам словаря `auth`, без деталей |
| R-5 | MUST: оболочка не рендерится для `REGISTRATION`, `REQUEST_PENDING`, `REJECTED` (кроме профиля — вид без оболочки) |
| R-6 | SHOULD: предзаполнение ФИО из провайдера; редактируется |
| R-7 | SHOULD: `noindex` на `/login`, `/register`, `/pending`, `/privacy` |

## 16. Acceptance criteria

- [ ] Вход через Telegram создаёт `REGISTRATION` (с `username` и `phone`, если переданы) и ведёт на `/register`; администратор входит по email и паролю — исход: ручной smoke (dev).
- [ ] Без согласия кнопка «Отправить заявку» неактивна; обход клиента даёт `VALIDATION` — исход: ручной шаг + тест контракта.
- [ ] После отправки пользователь на `/pending`; повтор отправки не создаёт вторую заявку — исход: тест.
- [ ] Отклонённая заявка показывает причину; «Исправить» ведёт на `/register` — исход: ручной шаг.
- [ ] Привязка чужого Telegram id отклоняется с нейтральным сообщением; последний способ отвязать нельзя — исход: тест.
- [ ] Запрос на удаление создаётся, отменяется; второй открытый не создаётся — исход: тест.
- [ ] `/privacy` открывается без сессии и показывает версию — исход: ручной шаг.
- [ ] На `/register` и `/pending` есть «Выйти» — исход: проверка DOM.

## 19. Agent notes

- Не вызывать серверный `signIn` для Telegram; вход и привязка — клиентские.
- Не отмечать чекбокс согласия по умолчанию и не активировать кнопку без него.
